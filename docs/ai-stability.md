# Dailic AI 질의·해설 안정화 기록

## 범위와 결과

- 기준: `Team-Dailic/Backend`의 `develop`, 커밋 `c060099883e17072945172d04393252e6b881777`.
- 로컬 작업 브랜치: `codex/chatbot-stability`. 원격 저장소에 push하거나 서비스를 배포하지 않았다.
- 대상: `/ai/ask/{problemId}`, `/ai/explain/{problemId}` 및 OpenAI 호출 설정.
- 현재 구현은 문제와 질문을 매번 전달하는 단일 질의·해설 방식이다. 대화 이력을 저장하는 다중 턴 챗봇은 아니다.
- 실제 OpenAI API를 호출하지 않고, 모의 HTTP 응답과 로컬 지연 서버로 검증했다.
- 2026-09-25 검증: 전체 37개 테스트 통과. AI 계약 테스트 33개, 실제 HTTP 읽기 타임아웃 테스트 1개, 기존 테스트 3개.

## 발견한 문제와 수정

| 상황 | 기존 동작 | 수정 후 |
|---|---|---|
| OpenAI가 429 또는 오류 반환 | 오류 문구를 답변 문자열로 반환하여 컨트롤러가 HTTP 200으로 포장 | 429·5xx는 HTTP 503, 기타 외부 API 오류는 502 |
| 외부 API 응답 지연 | 이 호출 전용 연결·읽기 제한시간이 명시되지 않음 | 연결 5초, 읽기 30초를 기본값으로 설정. 타임아웃은 504 |
| 질문 누락·공백·지나치게 긴 입력 | 요청 DTO 검증 없이 서비스로 전달 | 공백 제외 내용 필수, 최대 4,000 Java 문자열 길이. 잘못된 요청은 400 |
| 외부 응답의 choices/message/content 누락 | 오류 문구를 정상 응답으로 전달하거나 예외 발생 | 응답 구조·비어 있는 본문 검사 후 502 |
| 설정 누락 | 호출 실패 또는 API 키 로그 처리 중 예외 가능 | 키·모델 등이 없으면 외부 호출 없이 503 |
| 로그 | 질문·프롬프트·외부 오류 본문, API 키 일부 출력 | 해당 출력 제거. 호출 성공 여부·경과시간·외부 HTTP 상태 기록 |
| 설정 예시 | `openai.api.key`, `openai.api.url`이 실제 프로퍼티와 불일치 | `openai.key`, `openai.url`로 통일하고 환경변수 설정 추가 |

`ask`와 `explain`의 중복 호출 코드를 합쳐 같은 실패 처리 규칙을 사용한다. 성공 응답인 `data.answer` 구조와 `includeSolution`에 따른 기존 해설 포함 여부는 유지했다. 요청 한 번에 애플리케이션에서 외부 호출 한 번을 수행하며 자동 재시도는 추가하지 않았다.

429의 원인은 일시적인 요청 제한일 수도, 계정 사용량 문제일 수도 있다. 원인 구분 없이 반복 호출하는 재시도 정책은 이번 범위에 포함하지 않았다. 계정 문제는 별도로 확인해야 한다. 참고: [OpenAI 공식 Rate limits 안내](https://developers.openai.com/api/docs/guides/rate-limits).

## 재현과 검증 근거

수정 전 코드에 먼저 적용한 동일한 12개 시나리오에서는 정상 응답 1개만 통과했고 오류 상황 11개가 실패했다. 수정 후 같은 시나리오가 통과했으며, 경계값과 추가 오류 상황까지 확장한 AI 계약 테스트 33개도 통과했다. 이 숫자는 테스트 시나리오 수이며 운영 성공률이나 실제 장애 발생 횟수가 아니다.

검증한 상황:

- 정상 답변의 HTTP 200, `data.answer`, 모델 및 Authorization 전달.
- 질문 누락/null/공백, 4,000자 허용, 4,001자 거절, 잘못된 JSON·문제 ID·사용자 ID 누락.
- OpenAI 429, 400/401/403/404, 500/502/503, 연결 실패, 타임아웃.
- 외부 응답의 비어 있는 목록·필드, 빈 답변, JSON 파싱 실패.
- API 키 누락, 없는 문제, 문제 본문 누락, 기존 해설 포함 여부.
- 별도 로컬 HTTP 서버가 응답을 지연할 때 실제 읽기 제한시간 동작.

로컬 지연 테스트는 읽기 제한을 150ms로 설정하고 504 예외, 4초 이내 종료, 서버가 받은 요청 1회를 확인한다. 150ms는 테스트를 빠르게 실행하기 위한 값이다. 운영 응답속도가 150ms라는 의미가 아니다. 연결·읽기 타임아웃은 전체 요청의 엄격한 총 실행시간 제한과도 다르다.

전체 테스트를 실행하기 위해 기존 테스트의 노후화도 수정했다. LicenseControllerTest의 문자열 자격증 데이터를 현재 License 엔티티 및 응답 구조에 맞추고, DB 컨텍스트 테스트에는 테스트 전용 메모리 H2를 지정했다. 저장소 테스트에는 필수 자격증 관계를 넣었다. 운영 DB 설정을 이 테스트 설정으로 바꾸지는 않았다.

재실행(Java 17):

```sh
./gradlew test --no-daemon --no-watch-fs
```

AI 검증만 실행:

```sh
./gradlew test --tests '*AIControllerContractTest' --tests '*AITransportTest' --no-daemon --no-watch-fs
```

새 환경에서는 Gradle 의존성 다운로드가 필요할 수 있다. 테스트는 실제 OpenAI API 키나 유료 호출이 필요하지 않다.

## 서버 설정과 모바일 연동

실제 호출 시 실행 환경에 `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정한다. 기존에 사용하던 Chat Completions 호환 모델을 명시해야 한다. 새 모델을 임의로 선택하거나 마이그레이션하지 않았다. 키는 소스코드나 이 문서에 넣지 않는다.

선택 설정:

| 환경변수 | 기본값 |
|---|---|
| OPENAI_API_URL | https://api.openai.com/v1/chat/completions |
| OPENAI_CONNECT_TIMEOUT_MS | 5000 |
| OPENAI_READ_TIMEOUT_MS | 30000 |

타임아웃 설정값은 1 이상이어야 한다. API 키·모델이 없는 경우 다른 기능을 위한 서버 시작은 허용하되 AI 요청은 503을 반환한다.

모바일 클라이언트가 수정 전의 HTTP 200만 가정한다면 함께 수정해야 한다. HTTP 실패 응답의 `message`를 오류 안내로 표시하고, 성공·실패 모두 로딩 표시를 종료해야 한다. Retrofit 등에서 HTTP 실패 본문은 성공 본문과 다른 경로로 읽어야 할 수 있다. 이 저장소에는 앱 코드가 없어 화면 동작은 확인하지 못했다.

예시:

```json
{
  "status": 504,
  "message": "AI 응답 대기시간을 초과했습니다. 잠시 후 다시 시도해 주세요.",
  "data": null
}
```

앱에서 확인할 항목은 정상 답변 표시, 실패 시 로딩 종료와 안내, 연속 탭으로 인한 중복 전송, 뒤로가기 이후 늦게 도착한 응답 처리다. 현재 백엔드는 서로 다른 요청 간 중복 제거를 구현하지 않았다.

## 측정값의 의미와 남은 범위

`AI call outcome=... duration_ms=...`는 백엔드가 외부 API에 요청한 시점부터 응답 처리까지 걸린 시간이다. DB 조회와 모바일 네트워크·화면 렌더링 시간은 포함하지 않는다. 질문이나 정답을 로그에 남기지 않고도 호출 실패와 지연을 조사할 수 있도록 한 것이다.

실제 모델 답변의 정확성·일관성, 긴 답변의 중도 종료, 프롬프트 인젝션 대응, 동시 요청·사용자별 호출 제한, 비용 상한, 사용자 인증·권한, 대화 이력은 이번 검증 범위가 아니다. 실제 운영 응답속도 개선율이나 비용 절감률도 측정하지 않았다. 실서비스 적용 전에는 실제 설정으로 소규모 호출 및 앱 연동 확인이 남는다.

## 자소서·면접에 활용하는 방법

이 기록은 Codex가 코드 수정과 테스트 실행을 수행한 결과다. 본인이 직접 시나리오를 재실행하고 변경 이유를 이해한 뒤, 자신의 판단·구현·검증과 도구의 기여를 구분해 설명해야 한다.

직접 확인할 순서:

1. `AIControllerContractTest`의 `providerRateLimitIsNotASuccessfulAnswer`에서 429 응답을 어떻게 재현하는지 읽고 실행한다.
2. 기존 코드에서 왜 실패가 HTTP 200과 답변 문자열로 반환됐는지 확인한다.
3. `AIService`, `AIExceptionHandler`, `OpenAIConfig`를 따라가며 실패가 503/504로 바뀌는 흐름을 설명한다.
4. 앱에서 실패 화면과 로딩 종료까지 확인하고, 본인이 실제 수행한 내용만 작업 기록에 추가한다.

직접 이해·검증한 뒤 서술할 수 있는 경험의 구조는 다음과 같다:

> AI 질의 기능의 예외 상황을 점검하면서 외부 API 실패가 정상 답변으로 반환되는 문제를 확인했다. 실패 응답을 재현하는 테스트를 만들고 입력 검증, 타임아웃, 오류 응답 규칙을 정비했다. 수정 전후 같은 시나리오를 비교해 동작을 확인했다.

이 문장을 그대로 자신의 단독 구현 성과로 옮기지 말고 실제 역할에 맞춰 고친다. 면접에서는 ‘왜 HTTP 200이 문제였는지’, ‘실제 OpenAI 장애 없이 어떻게 재현했는지’, ‘왜 자동 재시도를 넣지 않았는지’, ‘서버 수정 이후 앱에는 무엇이 필요한지’를 설명할 수 있어야 한다.
